# Account delivery and revocation boundary

M13 adds a private account-side delivery path. No mutation tool, HTTP mutation route, startup wiring or provider write session is activated here. `operationPolicy` without `delivery` retains M12's parked behavior. Production composition must supply a real restore latch, current authorization policy, and the trusted provider grant-status lookup below.

## Trusted composition

```ts
type DeliveryGrantBinding = Readonly<{
  accountId: string; principal: string; backendUrl: string;
  grantId: string; clientId: string;
}>;

type DeliveryGrantStatus = Readonly<{
  accountId: string; clientId: string; active: boolean; scopes: readonly string[];
}>;

operationPolicy.delivery = {
  grantStatus: async (grantId: string): Promise<DeliveryGrantStatus | null> => {
    // return verified provider metadata, including inactive and expired grants.
    // do not return or look up a session or bearer.
  },
};

await actors.revokeDeliveryGrant(grantMetadata, commitRevocation);
await actors.resumeDelivery(activeFullContext, confirmOwnerDecision);
```

The provider's `PrivateGrant` structurally supplies the binding fields. Its `writeConnections.revoke(grantMetadata, commitRevocation)` lifecycle hook should call `actors.revokeDeliveryGrant` for every exact grant cutoff path, including standard OAuth revoke, provider session deletion, explicit revoke, repeat revoke and expiry. The provider must resolve the trusted binding before deleting its metadata. The actor enters the account FIFO lane, opens its owned account replica, durably records the grant cutoff and, if any outbox row remains, an account-wide pause. It then invokes `commitRevocation` once while still holding the lane. It never calls the revoked grant's `assertActive` afterward. If commit fails, the local barrier remains paused and the provider must report failure. The callback must not reenter the same actor lane. Revoking A does not change B's provider grant or bearer. A deadline while the revoke is still queued or reading the outbox aborts it before the cutoff, so the callback cannot run later. Once the cutoff commits, the deadline is disarmed and the provider callback completes under the lane; the caller receives that result rather than a timeout that might conceal a committed cutoff.

`resumeDelivery` accepts an active full `AuthContext` and a trusted callback that verifies the owner's explicit browser decision inside the same lane. M20 should call it only after authenticated CSRF-protected confirmation. The operation policy receives `action: 'resume'` before the callback and must verify the current provider grant and consent authority. A missing callback, a read session, read-only OAuth scopes, a revoked grant, a failed decision or a restore latch refusal cannot grant queue consent. The callback must not reenter the actor. Resume records permission only for the exact queued outbox IDs under the selected grant, clears the account pause, then attempts bounded delivery in the same lane. It cannot clear a restore latch, reconstruct missing provenance or execute a prepared intent.

The grant-status callback must return account and client identity, active state and current scopes from provider metadata. The provider's `deliveryGrantStatus(grantId)` can be wired directly; the coordinator keeps no grant cache. The provider gates `active` on its durable `credentialScope` and OAuth permission agreement; the account side also checks the exact request session is full. It compares the returned identity and scopes to the request and retained operation origin. A missing or inactive queued origin first seen through this lookup also persists an account-wide pause before a new mutation is admitted. A previously revoked origin covered by explicit owner resume does not re-pause the account merely because it remains inactive. The selected live grant is checked before each transport request, after awaited network work and before queue deletion. An upload-record reply is first handed to the journal's exact acceptance hook, then authority is checked, so a cutoff immediately after backend acceptance retains its local evidence. The callback must not load a stronger credential. The transport is created from the current request's exact full Snapback session and the existing backend URL; no session survives the actor turn.

## Queue rule

The product's `mutation_outbox` is shared by all grants and local fact recovery. Journal tuples map an outbox ID to its original operation and `operation_grants` row. A row with no matching tuple is unattributed, including read-derived facts and older local rows. Before a pass and each batch, the barrier examines the next 1,000 queued IDs. Any grant revocation with any queued row sets an account-wide pause, even when every queued row belongs to B. That pause blocks new mutations and every upload under all grants, while pull-only reads and status remain available subject to M12's prepared-intent and restore fences. It survives restart until explicit owner resume snapshots the next queue window and clears the pause in one durable transaction. Without a global pause, a current grant may deliver its own rows. Any row from another grant, a revoked grant, or an unattributed source requires a retained explicit owner-resume entry for that exact outbox ID and current grant. Later unattributed or foreign rows require another explicit resume when they reach the window; new unrelated rows are not swept into an earlier consent snapshot. New mutation admission pauses while the queue exceeds the bounded window, but resume can drain it in stages. The barrier survives actor eviction and process restart in a private, account-bound, version-checked `delivery.sqlite` sidecar. An independent `delivery_anchor` row in `operations.sqlite` binds the barrier to the account's operation generation. New operation histories write the anchor before the barrier initializes; a provider cutoff can create this empty operation history when none exists and no journal or command receipt needs preservation. The anchor marks barrier initialization durably before `delivery.sqlite` is created. If the initialized sidecar disappears, all delivery and new mutation admission fail closed. A pre-anchor operation history has unknown delivery provenance and fails closed regardless of whether a delivery sidecar remains; it is not silently adopted as a fresh account. Missing provenance requires trusted reconciliation outside owner resume.

The journal's `beforeDelivery()` checks for prepared work and original tool permissions, then publishes its current recovery head. The core sync engine's `delivery.authorize()` callback repeats current authority, queue and journal checks before provider creation and each batch. The real Snapback transport's `onUpload` awaits `journal.recordUploadAcceptance` for the exact record, digest, disposition and remote mutation stamp. The core's `delivery.beforeQueueClear(outboxIds)` repeats authority and queue checks, then awaits `journal.beforeQueueClear` before its exact outbox delete transaction. No queue count, empty queue or pull revision is treated as backend acceptance. A returned operation is reread from the journal after delivery, so its `state` and `delivery` reflect recorded acceptance; final metadata recounts pending local deliveries.

The account FIFO lane is the local linearization boundary. A provider revoke waits for an ongoing command transaction or delivery pass, then persists its cutoff before provider commit. A cutoff already visible to `assertActive` or `grantStatus` stops the next network step. If the backend accepted a record immediately before cutoff, that effect cannot be undone. The `onUpload` path attempts exact local acceptance recording before the next authority check; if publication then loses authority, the local chain retains the acceptance event and the queue remains for recovery under a later live grant. If the backend accepted a record but no response was received, the outbox remains and its idempotent wire identity is retried. A queued operation never executes its prepared core command under a different grant merely because delivery was resumed.

Account reads report `recovery.deliveryPaused` from the current grant and queue barrier. A permitted full grant with a queue inside one consent window reports `false`; a read grant, mixed queue without consent, queue beyond one window, or unconfigured delivery reports `true`. `recoveryReason` remains `delivery_barrier` while paused. Missing sidecar or provenance fails operation recovery with `OPERATION_PENDING` instead of presenting a normal paused status. Operation results and final metadata are reread after the pass, so a successful upload reports `backend_acknowledged`, its exact delivery disposition, and the updated pending count.

Delivery attempts at most three sync passes in one actor turn. Each pass freezes the highest ID in its first 1,000 queued rows. Before each batch and queue clear, the barrier refuses a row beyond that ID; an earlier batch deleting rows cannot slide the pass window onto ID 1,001. The incomplete pass reports attention and leaves any remaining rows queued. The actor request deadline, cumulative SDK fetch-count limit and 16 MiB of counted request/response bodies also apply. A pass that pulls new reconciliation work repeats only while the queue remains and the prior pass was otherwise complete. The inherited core engine and transport cap individual records/pages; no retry worker is scheduled. Offline, partial, revoked, unconsented and over-budget work remains queued and reports incomplete delivery. The internal operation result can still report `pending_sync` while a later owner session is needed. Public M14/M16 handlers must map internal results and report pending delivery honestly.

## Verification

`services/mcp/tests/delivery.test.ts` uses the real temporary Snapback server, production SQLite, exact full/read sessions and existing journal/head adapters. It covers independent grants, read-scope refusal, before-commit rollback, after-commit receipt capture, partial accepted upload, mixed queue restart/resume, missing sidecar and pre-anchor history refusal, queued and admitted revoke deadlines, a frozen 1,000-ID delivery boundary, read-derived facts and a retained restore latch. The test harness uses synthetic identities and the pinned Node 24.22.2 runtime.
