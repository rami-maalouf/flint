# M24 encrypted backup and restore controller

This tooling is staged, not installed or activated. It protects the separate MCP service without changing Snapback 0.4.49, mobile schema 12, native checksum gates or the existing backup timer. The parent must review it, rehearse on Oracle with synthetic accounts, and independently review before production use.

## Trust and storage boundaries

The service data root is `/var/lib/habit-system-mcp`. A complete stopped copy includes provider, vault, quote, product, sidecar and journal SQLite files plus WAL/SHM sidecars, account replicas and pending outbox. When `--paired yes` is selected, the same stopped interval includes the complete Snapback deployment `/var/lib/habit-system-fullstack/deployment`; sibling restore and runtime directories in its parent are excluded. The backup command stops only `habit-system-mcp@<reviewed-sha>.service` and, for a paired snapshot only, `habit-system-fullstack.service`. It restarts exactly those initially active units after snapshot processing, including failure cleanup. It does not stop the Traefik bridges or other VPS services.

The separate encrypted keys artifact holds `/etc/habit-system-mcp/config.json` and `keys.json`. It is not in the data archive. The external `restore-latch` is in neither archive. The age recipient is public on the VPS; the age identity stays on the Mac in `/Users/rami/Private/habit-system-mcp-age/`, mode 0700 with its identity file mode 0600, outside the checkout, app state and restore roots. Do not print, copy to the VPS, commit or include that identity in an archive. Protect the independent Mac controller log at `/Users/rami/Private/habit-system-mcp-controller/`, mode 0700, outside VPS and restored database snapshots.

The chosen encrypted off-host destination is `/Users/rami/Private/habit-system-mcp-backups/`, with one private 0700 directory per snapshot. After copying `bundle.json` and both `.age` files from the VPS, verify SHA256 against `bundle.json` on the Mac before calling it off-host. Retain seven daily and four weekly **verified** snapshots, pruning older copies manually only after the newest complete transfer and a restore rehearsal. This policy is not automated replication or retention. Until a verified Mac copy exists, a VPS staging archive is not an off-host backup. No measured recovery time or recovery point objective is claimed.

Before live use, the operator must arrange for `/run/habit-system-mcp-recovery` to exist as root-owned mode 0700, physically outside both backup roots. The staged `habit-system-mcp-recovery.tmpfiles.conf` provides the reviewed directory specification for installation; `/run` is ephemeral, so the directory must be recreated after reboot before recovery commands can run. The scripts fail closed when it is absent. `backup.mjs`, `mark-latch.mjs` and the native backend backup helper share its mode 0600 `lock.sqlite` and hold a Node 24 SQLite `BEGIN EXCLUSIVE` transaction. Both backup paths acquire it before unit inspection or stop and release it only after all restart attempts and active-state verification. Marking acquires the same lock before unit checks and releases it after the latch write. A competing process refuses without stopping or restarting anything. SQLite's process lock is released by the OS after SIGKILL; the retained lock file is not a stale ownership marker. Fixture tests use a private `--fixture-lock-dir` instead of the live path.

## Native backup timer coordination

The existing daily timer and every manual native backup continue to call `/opt/habit-system-fullstack/backup.sh /var/backups/habit-system-fullstack`. Install the reviewed `ops/backup-oracle.sh` at that exact entry point. Place the reviewed `ops/mcp/recovery/` tree in a root-owned immutable versioned directory such as `/opt/habit-system-mcp/tools/releases/<reviewed-artifact-sha>/recovery/`, then point `/opt/habit-system-mcp/tools/recovery/` at that directory. Point `/opt/habit-system-mcp/tools/node` at the checksum-verified Node 24.22.2 executable. The recovery path must include its relative `common.mjs`, `lock.mjs` and `systemd.mjs` imports. Prepare the root-owned private recovery lock directory with tmpfiles and keep `/var/backups/habit-system-fullstack` pre-existing, root-owned and mode 0700. Finish these steps before activating MCP or allowing a paired snapshot. Review the installed file hashes and symlink targets; the paths above are an installation contract, not a claim that the tools have been installed.

When MCP config, state, recovery tools or the lock directory is present, the shell entry executes `native-backup.mjs --output-dir <existing-private-dir>` through that pinned Node. A missing helper, runtime or lock refuses before a systemd call. The helper takes the same recovery lock, records whether `habit-system-fullstack.service` was active, stops it only if active, confirms inactivity before archiving, and restarts it only if it was initially active. A stop that reports failure after deactivation still triggers that restart. The lock remains held through archive fsync, every restart attempt and verification of the original active state. Only then does it print the archive path. It retains a complete archive if restart verification fails, exits nonzero and requires operator assessment. A tar failure removes its partial archive and attempts the required restart. The format stays `habit-system-<UTC>.tar.gz` containing `deployment/` with native release metadata, SQLite and sidecars. The helper does not encrypt or transfer this legacy native archive. Its output must remain private and be moved to independent storage under the existing native policy. An abrupt process death can leave the service stopped and a partial archive; the operator must inspect unit state and incomplete output before retrying. Before any MCP marker exists, the shell retains the legacy backup path, with restart cleanup armed before stop and no restart of an initially inactive backend.

These hashes match the [official release asset digests](https://api.github.com/repos/FiloSottile/age/releases/tags/v1.3.2). It takes an existing empty private output directory and requires `uv` for its Python safety check. The test requires `MCP_AGE_BIN` and `MCP_AGE_KEYGEN_BIN` in CI; absence fails the test rather than skipping it.

```sh

```

## Backup API

Run `backup.mjs` with pinned Node 24.22.2 after a reviewed M23 release has been installed. The output directory must already exist, be empty, owned by the invoking user and mode 0700. It must be physically outside both `/var/lib/habit-system-mcp` and `/var/lib/habit-system-fullstack`; the script checks this before any service stop. Preflight requires exactly the named MCP release active and all requested units active. It records all initially active units before stopping any, requires no MCP release active and, for a paired backup, the backend inactive before copying, and attempts to restart every initially active unit even if a stop reports failure after deactivation. The service and optional backend stay stopped while the full data and key snapshots are copied and encrypted. The script refuses unrelated symlinks, hardlinks, world-writable directories, unsafe output directories and excessive entries/files. Snapback 0.4.49 creates three group-writable directory shapes beneath its private 0700 backend root: `releases`, `releases/<positive-release-number>`, and `releases/<positive-release-number>/snapback`. Only these exact paths are admitted with group write, and they must have the same owner and group as the backend root; `assets`, `.snapback4`, other release children and deeper descendants remain restricted. One native relative link shape is admitted: `backend/releases/<positive-release-number>/.snapback4/store.sqlite -> ../../../store.sqlite`. Its target must resolve physically to the regular, singly linked `backend/store.sqlite` with the same owner and group. The manifest authenticates the link type, target text and target file digest; tar validation and restored-tree checks enforce the same shape. The complete backend graph, including release metadata and SQLite WAL/SHM sidecars, remains in the paired archive. No source permissions are changed. Isolated extraction strips group-write permissions from restored directories; the rehearsal must confirm the restored Snapback release remains usable. Temporary plaintext tar files are private and removed on normal exit. Each encrypted artifact is fsynced, SHA256 recorded, and the outer `bundle.json` written last with file and parent fsync. After all restart attempts, while still holding the recovery lock, the script requires exactly the expected MCP release active and the paired backend active. Only then can it release the lock and report the snapshot ready. A zero exit from `systemctl start` alone does not establish restart success. Do not treat a script success message as proof of off-host transfer.

For paired live backup, the backend source is exactly `/var/lib/habit-system-fullstack/deployment`, the directory passed to `snapback4 serve`. The surrounding `/var/lib/habit-system-fullstack` remains the exclusion boundary for output paths. The encrypted archive maps the deployment's contents to `backend/`, so it contains `backend/store.sqlite`, `backend/releases/...` and their authenticated native link. It does not contain a `backend/deployment/` layer or unrelated sibling restores and runtime directories from the parent. The existing native backup remains a separate tar with `deployment/` as its top-level member. An isolated paired restore's `target/backend` is a fresh deployment directory; this tool never replaces the live parent or deployment. Any later production replacement procedure must use that exact boundary and receive its own review. Fixture-only `--fixture-live-layout yes` selects `deployment` beneath `--fixture-backend-root` to test the same source rule while retaining the parent output exclusion.

```sh
sudo /opt/habit-system-mcp/releases/<sha>/node/bin/node /opt/habit-system-mcp/recovery/backup.mjs \
  --live yes --paired yes --release-sha <sha> \
  --recipient <public-age-recipient> --age-bin /opt/habit-system-mcp/tools/age \
  --output-dir /var/backups/habit-system-mcp/staging/<new-snapshot-directory>
```

For a service-only backup, omit `--paired yes`; it cannot establish a consistent paired backend point. The staging directory and script installation are operator actions after review. No command here creates a production user, directory, key or latch. Keep the existing complete Snapback backup and its retention separate. Do not use phone sessions, migration exports or real accounts as rehearsal fixtures.

An abrupt process death can leave stopped units and private plaintext `.snapshot-*` scratch in the staging directory. The OS releases the recovery lock, but it does not restart services or erase scratch. Before handling that directory, the operator must verify no recovery process owns the lock, record the failed snapshot state, inspect the exact stopped units and incomplete output, and securely remove the scratch under the same private directory after review. A completed `bundle.json` and encrypted artifacts remain on disk if restart verification fails; the command exits nonzero and does not print a ready message. Preserve and assess that potentially valid artifact separately from the failed service restart. Never treat a partial encrypted artifact or a restarted unit alone as a completed backup.

## Restore intent and isolated rehearsal

Install `uv` on the Mac controller before isolated restore; the archive safety validator runs through `uv run --no-project python`.

The Mac controller command first appends a JSON restore intent with a fresh UUIDv4 to `restore-intents.jsonl` and fsyncs both file and parent. The archive's `bundle.releaseSha` identifies the release that produced the snapshot. The separate mandatory `--current-release-sha` identifies the release serving now; the controller records both and passes the exact intent UUID as mandatory `--restore-intent-id` to `mark-latch.mjs`. Only after the durable intent does it SSH to Oracle with `BatchMode=yes` and run that marker under sudo. The remote command holds the recovery lock, validates the private latch's exact installation header and bounded unique UUIDv4 tail, and enumerates active `habit-system-mcp@*.service` units. For the first mark it requires exactly the named current release, stops it through systemd's bounded graceful shutdown, stops the named Snapback unit for a paired archive, and requires the backend inactive and no MCP release active. A later restore on an already marked, stopped pair may append a new UUID after the same quiescence check; an active release must still match `--current-release-sha` and be stopped. A different or ambiguous active release, a unit that remains active after stop, a corrupt or legacy-only latch, or a reused older UUID refuses the mark. It appends exactly `restored <intent UUID>\n` with file and directory fsync before any database replacement. Each new intent changes the hash-based issuing epoch, even if the old database pair is restored again. After success the controller appends a second durable `latch_marked` receipt with the same intent ID. It never starts services or clears/provisions a latch. A failed remote mark leaves an intent without a receipt, and isolated restoration refuses it. Record the installation ID outside either database pair when first provisioned; do not derive a new one from a restored config.

If SSH loses the response after the latch fsync but before the off-host receipt, the controller retains an intent without `latch_marked`. The VPS may already be write-fenced. Keep units stopped and writes fenced, inspect the latch and active-unit inventory read-only, and preserve the controller log. A controlled retry uses `restore-intent.mjs --retry-intent-id <retained UUID>` with the same bundle, installation, current release and paired setting. The Mac verifies the unresolved intent in its private log before the remote call. The marker can verify that its last record already contains that UUID only while every named unit remains stopped, then return without appending it again; the Mac fsyncs the missing receipt. A superseded UUID, missing retained intent, existing receipt or newly active unit refuses retry. An earlier ambiguous attempt that did not append a marker may require the original active-unit preflight or operator reconciliation. Never invent a receipt or treat an SSH timeout as a successful mark.

Run the production marker only through the Mac controller. The VPS marker checks the supplied UUID, latch and unit state; it cannot independently read the retained off-host Mac log. A new restore request is refused while that controller has an unresolved intent for the installation.

```sh
/path/to/node-24.22.2 ops/mcp/recovery/restore-intent.mjs \
  --controller-dir /Users/rami/Private/habit-system-mcp-controller \
  --bundle /Users/rami/Private/habit-system-mcp-backups/<snapshot>/bundle.json \
  --installation-id <original-id> --current-release-sha <currently-active-reviewed-sha>
```

For a lost-response reconciliation, use the same command and arguments with `--retry-intent-id <UUID-from-retained-controller-log>`. This is a retry of one durable intent, not a new restore. It can complete only after the stopped-unit check; an existing receipt refuses another attempt.

After the intent succeeds, `restore-isolated.mjs` runs on the Mac with the off-host identity. It rechecks the remote latch and requires its last UUID to match the latest completed off-host intent for this installation and bundle. It checks both encrypted file hashes, decrypts with age into a private temporary directory, validates tar paths/types/size and every file digest, and atomically creates a **new absent** isolated target. It refuses `/var/lib/habit-system-mcp`, `/var/lib/habit-system-fullstack`, `/etc/habit-system-mcp` and `/opt/habit-system-mcp` as targets or descendants. The restored `keys/` directory is separate from `state/`. Never point a production unit at the rehearsal target or copy it over live data. Transfer to an empty Oracle rehearsal root and test there only after another review.

```sh
/path/to/node-24.22.2 ops/mcp/recovery/restore-isolated.mjs --offhost yes \
  --bundle /Users/rami/Private/habit-system-mcp-backups/<snapshot>/bundle.json \
  --identity /Users/rami/Private/habit-system-mcp-age/identity.txt \
  --age-bin /private/empty-age-tools/age/age \
  --intent-log /Users/rami/Private/habit-system-mcp-controller/restore-intents.jsonl \
  --installation-id <original-id> --target /Users/rami/Private/habit-system-mcp-rehearsals/<new-name>
```

The test-only `--fixture-root` mode requires `MCP_RECOVERY_FIXTURE=1` and a private `--fixture-lock-dir`; it exercises the same archive/controller/extraction code without SSH. Its optional private `--fixture-systemctl` binary exercises the same active-unit inventory, stop and recheck logic against an isolated fake. It cannot be used as a substitute for an Oracle rehearsal. Before real restoration, stop admission and service, preserve the original failed directories and uncertainty, and mark the latch **before** replacing any part of the MCP/backend pair. The current scripts deliberately never replace production paths. A later production restoration procedure must keep this ordering and receive its own independent review.

## Fencing and limits

`FileRestoreLatch` is the startup and per-publication gate. A marked, missing or malformed latch fences mutations even if an old MCP journal and backend recovery head match. The runtime hashes the full validated marker to bind OAuth issuing authority to this restore epoch; missing, corrupt and legacy-only markers remain degraded. This tooling has no clear, reprovision, resume or forced-write action. A restored deployment may offer only the runtime's separately validated degraded read path. Missing age identity or keys archive, damaged ciphertext, untrusted tar entries and inconsistent manifests refuse extraction. Structurally incomplete operation sidecar/journal pairs also refuse extraction, except for the archive-admission case below. Complete retained journals are accepted; the runtime checks their ancestry and remote head before a restored product read.

One narrow **archive-admission** exception accepts a pre-first-mutation delivery-only `operations.sqlite` with no journal: exact v1 sidecar and delivery schemas, a matching initialized replica marker and account identity, valid shared generation, `journal_ready=0`, initialized delivery anchor, and empty operation origins, owner resumes and product command receipts. A product mutation outbox table may retain read-derived or unattributed rows; the tool validates that it is a table, copies every row unchanged, and never uploads, regenerates or clears it. The latch stays marked, and the isolated tool never creates a journal or checks the owner-scoped remote recovery head.

Accepting that archive does not admit a product read from it. With the restore latch marked, an initialized account without a journal still refuses product reads and requires trusted reconciliation. The ordinary delivery-only read exception requires a ready, unrestored latch, a null remote head and retained initialized product binding; it is not used after restoration. Restored accounts with complete retained journals use the separate ancestry and exact-head checks described in `operation-runtime.md`. An isolated archive copy does not establish complete operation history. Do not create a new journal or operation ID to hide uncertainty.

The off-host log and latch are process/procedure controls, not an automatic monotonic witness of every operation. A privileged whole-VPS rollback that bypasses this controller can restore an old ready marker and matching databases without detection. A whole-VPS restore must be initiated by this independent controller before the VPS is exposed to writes. If that cannot be established, writes stay fenced. There is no implemented proof that complete history is independently reconstructable and no automatic unfence.

## Synthetic evidence and pending gates

`services/mcp/tests/backup-restore.test.ts` uses real Node 24.22.2 SQLite and real age 1.3.2. It starts with synthetic provider, vault, quotes, account replica, product, delivery, operation, journal and backend SQLite databases, keeps WAL sidecars open through the snapshot, advances local and backend databases after backup, records a controller intent, marks the real `FileRestoreLatch` format, decrypts the old matching pair and reads back every named store and pending operation while writes stay fenced. Distinct restore intents append distinct latch UUIDs and change the runtime's issuing generation. A retained off-host intent with a lost response can be retried while the named units remain stopped; an old receipt cannot authorize a later marker. A pre-first-mutation revoked delivery sidecar round trip restores without creating a journal and preserves a queued unattributed product fact while the latch stays marked. Variants with initialized-but-missing journal, unknown generation or replica marker, operation origins, owner resumes, mismatched delivery identity, product receipts, or journal without sidecar refuse an isolated target. A second native-layout fixture includes 0775 backend release descendants and the exact relative store link, then decrypts and reads a SQLite record through that link while fenced. Adversarial backup fixtures reject foreign, absolute, incorrect and chained links, world-writable descendants and hardlinked stores before encryption. Crafted tar fixtures reject foreign and chained links before extraction. These fixtures reproduce the stopped SDK layout but do not execute the SDK or prove its schema. Wrong identity and damaged ciphertext each refuse an isolated target. An isolated systemd fake proves archive A can be restored while release B is active, and that an ambiguous or non-stopping MCP unit cannot precede a latch mark. The backup fixture refuses an output path under either root before any fake stop call; it also refuses an extra active MCP release and a stop that returns success while leaving one active. A stop that reports failure after deactivation triggers restart attempts for all initially active units. A start that exits zero but leaves MCP inactive, activates the wrong or an extra release, or leaves the paired backend inactive retains the encrypted artifact but exits nonzero without a ready message. Concurrent processes prove a second backup and restore marker cannot enter while backup holds the SQLite lock, and SIGKILL releases that OS lock. These prove local fixture and process logic, not Linux power-loss ordering, actual Oracle systemd stop/start, Snapback SDK convergence, public TLS routing, off-host transfer automation or production restore. The parent owns those rehearsals and the M25 review gate.
